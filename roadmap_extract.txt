Versione documento:
 
1.0
Obiettivo:
 
trasformare GrigliaTron da web app funzionante per singolo evento a piattaforma collaborativa modulare, mobile-first e pronta per evoluzione open source.
Destinatario:
 
sviluppatore AI / agente di coding / Antigravity
Ruolo guida:
 
capo sviluppatore / product owner tecnico
1. Visione del progetto
GrigliaTron nasce come gestionale leggero per organizzare una grigliata tra amici, ma l’utilizzo reale ha dimostrato che il concetto è valido anche per altri eventi informali: compleanni, cene, uscite, weekend, feste, ritrovi e piccoli viaggi.
L’obiettivo della prossima evoluzione è trasformarlo in una web app collaborativa più matura, mantenendo però tre principi fondamentali:
Semplicità assoluta per l’utente finale
L’utente deve capire subito cosa fare, senza sentirsi davanti a un gestionale complesso.
Mobile-first reale
La versione mobile è prioritaria. L’utente deve avere tutto chiaro dalla prima schermata, senza dover scrollare a lungo.
Architettura modulare e open-source ready
Il codice deve essere pulito, scalabile e pubblicabile in futuro su GitHub, senza dati personali, credenziali o logiche hardcoded.
2. Problema emerso dall’uso reale
Durante l’evento reale, GrigliaTron è stato chiaro e apprezzato dai partecipanti. Tuttavia è emerso un problema UX importante:
Nella versione mobile, la dashboard risultava troppo lunga. Per vedere tutte le sezioni bisognava scrollare molto, e questo rendeva l’esperienza più scomoda e potenzialmente confusionaria.
La soluzione non è ridurre le funzioni, ma riorganizzarle.
La nuova versione deve evitare la dashboard infinita e introdurre una navigazione più simile a una vera app.
3. Obiettivo UX principale
La prima schermata deve essere un
 
centro di comando compatto
.
Da mobile, appena l’utente apre GrigliaTron deve capire immediatamente:
che evento sta guardando;
quando e dove si svolge;
cosa riguarda lui direttamente;
se deve portare qualcosa;
se deve pagare qualcosa;
se ci sono sondaggi aperti;
se ci sono aggiornamenti importanti;
quali sezioni può aprire.
Non deve più essere costretto a scorrere tutte le sezioni una dopo l’altra.

9. Gestione quote e pagamenti
9.1 Obiettivo
La sezione spese deve diventare una vera gestione quote.
Il sistema deve calcolare:
totale spese;
numero quote;
quota singola;
quanto ogni persona ha anticipato;
quanto ogni persona deve pagare;
quanto ogni persona deve ricevere;
trasferimenti consigliati tra partecipanti.
9.2 Principio fondamentale
Il numero di quote non deve necessariamente coincidere con il numero reale di partecipanti loggati.
Esempi:
una coppia può valere 2 quote;
un bambino può valere 0 quote;
una persona può valere 0.5 quote;
l’admin può impostare un numero totale quote manuale.
9.3 Campo quote per partecipante
Ogni partecipante deve avere:
quoteCount
Esempi:
Giammario: 1
Marco: 1
Coppia Rossi: 2
Bambino: 0
Quota ridotta: 0.5
9.4 Formula base
Totale spese = somma di tutte le expenses.amount
Totale quote = somma quoteCount dei partecipanti paganti
Quota singola = Totale spese / Totale quote
Quota dovuta utente = Quota singola × quoteCount utente
Totale anticipato utente = somma expenses dove paidBy === userId
Saldo utente = Totale anticipato utente - Quota dovuta utente
9.5 Interpretazione saldo
Saldo > 0 → utente deve ricevere soldi
Saldo < 0 → utente deve pagare soldi
Saldo = 0 → utente è in pari
9.6 Esempio
Totale spese:
150 €
Quote paganti:
8
Quota singola:
18,75 €
Spese anticipate:
Marco: 80 €
Luca: 70 €
Se Marco e Luca hanno entrambi quotaCount = 1:
Marco deve ricevere: 80 - 18,75 = 61,25 €
Luca deve ricevere: 70 - 18,75 = 51,25 €
Gli altri partecipanti con saldo negativo dovranno versare fino a compensare questi crediti.
10. Override manuale delle quote
L’admin deve poter scegliere tra due modalità:
Modalità A — Quote per partecipante
Il sistema usa la somma dei
 
quoteCount
 
dei partecipanti.
Modalità B — Totale quote manuale
L’admin imposta manualmente:
manualTotalShares
Se
 
manualTotalShares
 
è valorizzato, il sistema usa quello per calcolare la quota singola.
Questa modalità serve quando l’admin vuole dividere per un numero stabilito, anche se i partecipanti registrati non sono allineati.
11. Pagamenti consigliati
11.1 Obiettivo
Il sistema deve suggerire chi deve pagare chi.
11.2 Input
Lista utenti con:
balance
Dividere in:
creditori = utenti con balance > 0
debitori = utenti con balance < 0
11.3 Output
Generare una lista:
[
  { fromUserId, fromUserName, toUserId, toUserName, amount }
]
11.4 Algoritmo
Ordinare debitori e creditori.
Prendere il primo debitore.
Abbinarlo al primo creditore disponibile.
Generare trasferimento per l’importo minimo tra debito residuo e credito residuo.
Aggiornare i residui.
Continuare fino a saldo zero.
Arrotondare a 2 decimali.
11.5 UI
Mostrare una sezione:
Pagamenti consigliati
Esempio:
Anna → Marco: 18,75 €
Paolo → Luca: 18,75 €
Ogni riga può avere pulsante PayPal se disponibile.
12. PayPal
12.1 Strategia iniziale
Non integrare API PayPal nella prima versione.
Usare invece link PayPal configurabili, più semplici e open-source friendly.
12.2 Campi partecipante
Ogni partecipante può avere:

paypalEmail
12.3 UI
Se un partecipante deve ricevere soldi e ha
 
paypalLink
, mostrare:

12.4 Nota
La gestione reale dello stato
 
“pagato/non pagato”
 
può essere implementata successivamente. Per ora il sistema deve suggerire i pagamenti e facilitare l’apertura del link.
13. Foto evento e PDF ricordo post-evento
13.1 Obiettivo
A fine evento GrigliaTron deve trasformarsi anche in archivio/ricordo dell’esperienza.
Quando l’evento viene concluso, il sistema deve notificare l’admin via email chiedendogli di caricare una
 
foto evento ufficiale
. Questa immagine diventerà:
immagine principale dell’evento nella GUI;
copertina del riepilogo post-evento;
immagine principale del PDF ricordo.
Il sistema deve poi generare un PDF ordinato, bello e leggibile con tutti i dati principali dell’evento.
13.2 Flusso operativo
Quando l’admin imposta lo stato evento su:
concluso
oppure quando la data evento è passata e l’admin conferma la chiusura, GrigliaTron deve:
inviare una email all’admin;
chiedere di caricare la foto evento;
mostrare nella dashboard admin una card dedicata:
Carica foto ricordo evento
salvare la foto su Firebase Storage;
aggiornare il documento evento con l’URL dell’immagine;
usare la foto come immagine hero dell’evento;
permettere la generazione/download del PDF ricordo.
13.3 Email all’admin
L’email deve essere inviata solo all’admin o agli admin evento.
Oggetto suggerito:
[GrigliaTron] Evento concluso: carica la foto ricordo
Corpo email suggerito:
L’evento “Grigliata in montagna” risulta concluso.
Carica una foto ricordo: diventerà l’immagine principale dell’evento e verrà usata per generare il PDF riepilogativo.
Se disponibile, includere link diretto alla pagina evento.
13.4 Dati evento da aggiornare

14. Notifiche email per aggiornamenti evento
15.1 Obiettivo
Quando viene pubblicato un aggiornamento importante o urgente nella sezione Aggiornamenti, i partecipanti devono poter ricevere una notifica email.
Gli utenti hanno effettuato login con Google, quindi l’app conosce la loro email.
14.2 Principio di sicurezza
Non inviare email direttamente dal frontend tramite API private.
La soluzione consigliata è usare un sistema backend sicuro, preferibilmente:
Firebase Extension: Trigger Email from Firestore
oppure, in alternativa futura:
Cloud Function dedicata
14.3 UX aggiornamenti

Regole:

se tipo = urgente, checkbox attivata automaticamente;
se le notifiche email non sono configurate, checkbox disabilitata con tooltip.

17. Priorità tecnica immediata
La prossima attività da assegnare allo sviluppatore AI deve essere limitata e controllata.
Prompt operativo consigliato per il prossimo ciclo
Implementa GrigliaTron v1.1 concentrandoti solo su UX mobile-first e permessi utente.
Obiettivi:
1. Eliminare la dashboard mobile infinita.
2. Creare Home compatta con riepilogo evento, riepilogo personale e card sezioni.
3. Aggiungere bottom navigation mobile con tab: Home, Liste, Sondaggi, Spese, Info.
4. Spostare le sezioni attuali dentro le tab corrette.
5. Ogni card deve mostrare mini stato e badge numerico.
6. Implementare modifica/cancellazione degli elementi creati dall’utente.
7. Admin può modificare/cancellare tutto.
8. Non implementare ancora sondaggi, quote avanzate, scontrini foto o notifiche email: lasciare solo placeholder se necessario.
9. Non rompere Firebase Auth, Firestore e dati esistenti.
10. Verificare build locale e deploy Netlify.
Output richiesto:
- elenco file modificati;
- spiegazione sintetica della nuova navigazione;
- conferma build `npm run build` riuscita;
- eventuali migrazioni dati necessarie.
18. Note di qualità
Ogni implementazione deve rispettare questi principi:
mobile-first;
nessuna funzione deve rendere la Home confusa;
le funzioni avanzate devono stare in sezioni dedicate;
i dati devono rimanere sincronizzati via Firestore;
nessun dato sensibile nel codice;
ogni nuova funzione deve essere modulare;
UI semplice, leggibile, con pulsanti grandi;

19. Stato finale desiderato
GrigliaTron deve diventare una piccola piattaforma open source per eventi informali, con una UX così semplice che anche un gruppo di amici non tecnici possa usarla senza spiegazioni.
Il valore principale non è avere tante funzioni, ma coordinare un gruppo senza caos:
niente messaggi persi su WhatsApp;
niente doppioni nella spesa;
responsabilità chiare;
quote trasparenti;
aggiornamenti importanti notificabili;
organizzazione semplice;
riuso per eventi futuri;
codice pubblicabile e migliorabile dalla community.
